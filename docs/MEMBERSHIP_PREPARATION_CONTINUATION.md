# Explicit tracked preparation continuation

The selected manager/store API continueMembershipPreparation(token, operationId, envelopeHash) only stages an already admitted unresolved tracked membership command. The envelope hash is SHA256 of the exact canonical full receipt returned by discovery. It is not a new request ID or permission to create missing work. Schema3 and explicitly selected schema4 are supported without migration or default/UI routing changes.

Existing full proposal text and original canonical Version are authoritative. The exact enrolled application, target root, command envelope, frozen request, completed history and pending phase are revalidated under existing store/updater serialization. PREPARED captures the original; SNAPSHOT_RECORDED captures the persisted proposal; PROPOSAL_RECORDED stages it. The call stops at verified PUBLICATION_STAGED. Already staged only verifies. It never calls resume, retires/replaces canonical files, admits a UUID, publishes a catalog, acknowledges a result, adopts historical state or clears manager uncertainty.

All five operation-owned custody names are inventoried before writes and at boundaries. PREPARED requires none; SNAPSHOT requires only the exact recorded before copy; PROPOSAL also requires exact after copy; STAGED additionally requires its exact publication stage. Retired/conflict files are always absent. Matching-byte unrecorded files are ambiguous and remain preserved/blocked. There is no cleanup, overwrite, alternate-name retry or hash-only adoption.

A local per-step callback guard permits only that exclusive copy's transient destination while its existing capture owner runs. It is not an ownership proof from file kind. Exact captured Version is rechecked after the precommit callback before recording the phase, and retained dependencies are revalidated. The guard is local to this invocation and never survives restart. Boundary inspection is callback-free filesystem validation and does not re-enter SQLite or serialized methods. Actual expected next Intent is constructed from prior intent plus the captured receipt, not rebased from an arbitrary new history.

Durable phase-return loss can therefore be explicitly continued with the same token/UUID. Partial or complete copies without committed phase receipts remain NeedsReview. Cancellation and fatal failures retain existing classification/primary category; no automatic retry. A successful prepared result is not completed membership or permission to clear uncertainty. Later publication remains a separate explicit operation and is outside this increment.

Fixtures use real synthetic journal/store/manager authorities, same-byte inode swaps, root replacements, all-phase return losses, pending ordinary writer refusal, malformed identities, schema4 and cancellation/fatal paths. Injected callbacks/coroutine cancellation are not power-loss, device or global arbitrary-writer exclusion certification. VS Code lifecycle separation is a reference, not a durable retry schema to copy.

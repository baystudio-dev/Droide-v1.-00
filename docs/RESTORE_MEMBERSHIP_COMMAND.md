# Explicit restore-membership command receipts

This opt-in API integrates the actual ProjectManager restore-membership operation with JournaledProjectStore. Existing restoreWorkspace callers, default factories, startup choice, UI, selection/provider flows and ordinary saveCatalog remain unchanged. The command means only workspaceRemoved=false in the catalog, not successful opening, SAF preparation, human delivery, or editor handoff.

Call enableMembershipCommands explicitly on a selected store to enable journal schema3. It runs under that store's writes mutex and the shared updater/journal authority serialization. Pending work refuses migration. Existing completed schema2 receipts remain exact and are classified as untracked. Schema1-to2 retention enrollment remains its existing explicit step. A failed schema3 transaction leaves schema2 intact. Older code rejects unsupported version3.

The shared ProjectMembershipRestore plan retains the prior restore validation/normal behavior. The new manager restoreMembershipCommand freezes exact target/root identity, before catalog version and full proposal bytes. Its command token, operation UUID mapping and PREPARED operation commit together. The operation archive transaction commits the exact completed command result together with the completed operation and pending-slot removal. An already-restored target gets an atomically completed NO_CHANGE result without creating a fake operation.

The fixed durable recipient is manager-membership-service-v1. acknowledgeMembershipResult requires the exact token and outcome identity. It is deliberate service acceptance, not UI observation. Nothing automatically acknowledges after return/render/cancellation. Acknowledgement neither adopts historical catalog state nor clears manager uncertainty. An ordinary concurrent catalog writer can change current state before acceptance; historical result remains historical. A late change before manager adoption refuses and retains the uncertainty guard.

Discovery validates actual authority/receipt membership and is read-only. Lost admission returns are discovered from the command row, never guessed from matching bytes. Interrupted preparation is NeedsReview; no automatic capture, prepare, resume, replay or cancellation of pending work. Completed historical results never reapply restoration. A lost ack return can be explicitly repeated against the retained exact outcome. Unknown tokens cannot create operations.

Admission and acknowledgement retain all rows (later explicit no-change-only expiry is documented in MEMBERSHIP_NO_CHANGE_EXPIRY.md): configured entry cap at most128,2MiB serialized row cap,8MiB aggregate command-envelope budget, plus existing independent operation/custody budgets. Per-row and total completion/ack headroom are derived from exact serialized longest shapes before admission. Ack does not free capacity or reclaim payloads. No-change commands also consume command capacity. One unresolved command blocks new tracked commands; ordinary catalog writes still follow their existing pending/revision rules. No automatic eviction, floor advancement, payload deletion, retained-byte credit, or global closure claim.

Command rows and operation classifications have durable count/digest membership. Every tracked pending/completed operation maps bidirectionally to one exact command; legacy and ordinary operations are explicitly untracked. Missing/duplicate/foreign/malformed mappings, row omission, unsupported format, budget overflow and bad recipient/Unicode refuse. Canonical command proofs bind raw frozen intent plus proposal bytes and exact archived outcome. Root checks bracket durable admission/no-change/ack callbacks. These are cooperative authority and observed directory identities, not OS-wide external-writer exclusion or protection against a coherent rollback of all authority files.

Initial tracked commands require journal-owned proposal staging. An existing optional external stageProposal configuration is explicitly refused for migration/tracked execution, not silently bypassed. Its ordinary saveCatalog behavior remains intact.

Validation uses real synthetic-root selected-store/manager/journal fixtures, native-mode host SQLite and actual coroutine cancellation. Injected failures plus object recreation are not device power-loss certification. Source and runtime evidence live alongside the preserved checkpoint. No native rebuild, APK/device validation, default activation or full caller UI workflow is claimed.
